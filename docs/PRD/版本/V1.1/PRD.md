## 1. 目标用户与核心任务

### 为什么做这个个人项目

有小工具想法的非技术产品经理，需要把模糊需求变成明确范围，再判断 AI 生成的代码能否启动、是否符合原意。这个项目围绕这段从想法到可用结果的断点，把需求澄清、关键决策、PRD 确认、实现生成、本地检查和人工验收组织在同一工作台中。个人项目的首要价值是帮助用户完成一次真实的小应用制作，并在下一次需求出现时继续使用已有项目和产物。

这是基于项目设计与现有实现形成的产品问题定义，尚无系统用户访谈记录或效率对照实验支撑。个人创作动机不等同于已验证的普遍市场需求。2026-10-05 确定首批需求为产品经理的工作提效小工具，以及独立创作者的最小产品想法验证。两类需求共用“具体问题 → 小应用 → 真实任务验证 → 修改”链路。既有待办、记账、点单保留为历史样例；图像与视频类继续按独立样例验证，不把演示图或本地合成片等同于真实生成效果。

**当前用户事实：** 项目负责人于 2026-10-04 确认已有外部试用，尚未统计留存。外部试用人数、试用时间、任务完成数、协助程度与再次使用情况待补记录；当前不填写未经核对的用户数、留存率或付费成绩。

### 1.1 双角色（都要支持）

| 角色 | 是谁 | 核心任务 | 默认看到什么 |
| --- | --- | --- | --- |
| **产品发起人（PM 视图）** | 非技术产品经理、独立创作者 | 把具体工作问题或产品想法推进成可本地运行的小应用，用真实任务验证，按试用结果继续修改 | 对话、待办决策、PRD 摘要、预览、任务输入与试用记录；**不**看工厂仪表盘、原始闸门分数、底层证据堆 |
| **开发者** | 可协作的工程师 / 技术合伙人 | 查看与介入实现产物、复现运行、排查失败、必要时改约束后再跑 | 在 PM 视图之上增加：产物树、代码/日志、阶段证据、闸门明细、重跑与调试入口 |

同一「产品项目」内两种角色共用一套产线与产物；用**视图与权限提示**区分，不拆成两个互不相通的产品。

产品价值验证以产品经理和独立创作者能否完成自己的真实任务为主；两类发起人共用 PM 视图，不增加第三套工作台。开发者视图承担协作、诊断与结果复现，不能以开发者代操作成功替代发起人自主完成。

### 1.2 一句话价值

Agent造物坊是面向产品经理和独立创作者的 **小产品验证工厂**：围绕一个具体问题，生成可本地运行的小应用，用真实任务验证结果，再带着试用记录继续修改。交付包含应用及其验证依据；网页在线运行与公网交付留到下一步。

### 1.3 最小价值闭环

用户提交一个真实需求 → 回答关键决策并纠正理解 → 确认 PRD 和具体任务验收标准 → 获得实现与运行说明 → 本地检查 → 保存真实试用结果 → 未通过则基于当前成品修改下一版 → 任务通过后人工验收 → 下载应用与验证记录。

一次闭环的终点是「用户确认主路径可用且结果已归档」，不能把代码生成、测试通过、预览打开或自动闸门通过单独算成交付成功。用户需要工程协助时，记录为辅助完成；这仍是有效反馈，但与自主完成分开统计。

回访价值假设是：同一项目保留父子版本、原有代码、PRD、验收任务和试用记录，用户无需重新描述失败情况即可改进下一版。本轮明确实现“基于当前成品继续修改”，与仅从同一想法重新发起 Run 的失败重试区分；父版本保持可追溯。生成仍需经过原有人审和测试，不保证每次修改都成功，也不承诺任意外部代码仓库导入。回访价值需由第 4.4 节的外部试用记录验证。

### 1.4 差异化方向与首批场景

选择的差异化是“帮助发起人验证一个小产品是否解决真实问题”，落实为具体任务、失败记录回流和可检查的本地交付。需求澄清、生成代码、继续修改本身属于基础能力，不能单独宣称独有竞争壁垒。[Lovable 官方介绍](https://docs.lovable.dev/introduction/welcome)已覆盖自然语言构建、可编辑代码与部署；[Plan mode](https://docs.lovable.dev/features/plan-mode)也支持计划澄清、审核及迭代。本项目当前的重点和交付边界不同，不宣称这些能力优于或独有于对方。

| 首批人群 | 起始问题示例 | 要验证的结果 |
| --- | --- | --- |
| 产品经理 | 将散落的用户反馈整理为带原文依据的需求清单；将固定格式材料转成评审初稿 | 用真实材料检查遗漏、归类和结果可用性，记录人工修订点 |
| 独立创作者 | 将一个范围明确的计算、记录、清单或生成需求做成可试用的小产品 | 用至少三条具体任务判断主路径是否有用，记录失败后修改 |

上述为首批验证场景，不代表稳定成功率或外部用户验证结论。首页提供「把访谈变成需求」「收集读者的想法」「管理自己的小项目」三张场景模板卡，点击后填入可编辑的想法；模板不绕过需求确认，也不代表已有对应的专用生成引擎。本轮不增加企业权限体系、云托管、商业化、成品端埋点或试用邀请系统。下一步按真实试用记录决定是否扩展专用场景能力与在线能力。

## 2. 输入、过程与产物

### 2.1 输入
- 产品想法（一句话或短文）
- 确认前的补充与纠错；具体任务输入、预期结果；修改下一版时的变更要求与已有试用记录
- 可选：参考材料、已有 PRD 草稿、绑定的本地工作区目录（第一刀能力）
- 用户自备模型 API Key（工厂不垫付）

### 2.2 过程中人必须出现的点（人机边界）
以下三类 **必须人工完成**，Agent 不得自动跳过：

1. **决策**：改变方向、范围、成本、平台、数据隐私的选项（决策卡）
2. **确认**：PRD / 方案定稿确认后，才进入实现产线
3. **验收**：执行具体任务、记录实际结果并确认全部通过，同时完成本地运行等基础检查；失败记录可以先保存，未验收不得宣称交付完成

其余（检索、起草、生成代码、跑本地检查、整理产物）默认可自动，但高风险写盘/执行仍可要求确认（见第 8 节）。

### 2.3 产物（MVP）
- **产品项目**档案：想法、决策台账、PRD、Run 历史
- **可本地运行的小应用**：至少能在本机按说明启动，并完成主路径点选验证
- **运行说明**：如何启动、默认端口、验收步骤
- **试用与验收记录**：具体输入、预期结果、实际观察、通过与否、最终验收时间；失败记录保留供下一版修改
- **版本关系**：父版本及变更要求；新版本使用父版本 PRD、代码和试用记录作为上下文，原成品保留
- **完整本地交付包**：生成代码及目录结构、运行脚本与说明、PRD、决策、检查和验收记录、无真实密钥的环境变量示例；待验收下载明确标为待验收，不冒充已交付

### 2.4 非目标（本版明确不做）
- 一键公网生产上线、企业认证代办、多租户商业化计费
- 「一天一款」作为硬指标（先实测再定）
- 整盘复制工作台的 Electron / Arco / Rust / IM 渠道全家桶
- 把证据包打分、工厂 KPI 作为 PM 主界面核心信息

## 3. Agent 主链路（工厂产线）

### 3.1 对象模型（对标工作台，Web 重做）

| 对象 | 含义 |
| --- | --- |
| **产品项目（Project）** | 一个要被造出来的产品；可绑定工作区目录；侧栏按项目聚合 |
| **产线 Run** | 项目下的一次制造尝试（可多轮迭代）；有阶段状态机 |
| **会话** | 人与工厂的对话容器；从属于某次 Run（或项目级澄清会话） |
| **产物 Artifact** | PRD、代码、说明、预览入口等；**一等公民**，进产物树与预览区，不只塞聊天气泡 |
| **闸门 Gate** | 人审点（决策 / 确认 / 验收）或自动检查点（语法、能否启动）；人审不可自动通过 |

### 3.2 阶段（MVP）

```text
想法录入 → 澄清提问 → 〔人：决策〕→ 起草 PRD → 〔人：确认 PRD〕
→ 实现生成 → 本地可运行检查 → 〔人：验收〕→ 交付归档
```

- 自动段失败：进入可理解失败态，保留原因与重试入口
- 等待决策或确认 PRD 时：允许补充和纠正需求，保存反馈历史，重建 PRD 与待确认验收场景
- 任务验收未通过时：可以保存实际观察，基于当前成品开启子版本，携带失败任务进入下一轮；不得直接覆盖父成品
- 确认 PRD 前：开发者可看过程细节；PM 默认只看问答与 PRD
- 确认 PRD 后：实现在绑定工作区落盘（若已绑定），并在预览区打开

### 3.3 工作台布局（当前任务优先，按上下文呈现）

桌面选中 Run 后采用「项目导航 / 当前任务 / 项目资料」三栏，不把会话和编排拆成第四栏。未选中 Run 的首页隐藏无内容的资料栏，居中呈现想法输入与场景模板；已选中 Run 时移除创建新项目的输入框，避免把补充需求误提交为新项目。新建入口保留在导航中。

| 区域 | 职责 |
| --- | --- |
| **左栏** | 产品项目和 Run 列表、新建入口、基于已有项目/Run 数据的搜索、PM / 开发者视图切换 |
| **中栏** | 当前阶段工作卡和下一步动作优先；顶部展示「需求共创 → 构建应用 → 任务验证 → 交付迭代」四步进度；生成过程与历史记录默认折叠 |
| **右栏** | 项目资料、产物与预览、本地运行入口；PM 默认摘要/预览，开发者可看代码/日志/证据与工厂度量 |

编排是中栏内的状态与人审动作，不另开并排区域。手机与窄屏以当前任务为主体，导航和项目资料通过抽屉打开、关闭。实现沿用现有 Next + Tailwind 与 Lucide 图标。

确认前通过「需求文档与纠错 / 验收场景」页签分开审核内容，提供补充纠错和查看、修改当前决策的入口；实际可修改范围沿用原决策接口约束。PRD 以最新修订为准，历史稿有明确标识，验收场景未保存时不能确认构建。

任务验证展示实际记录数、通过数和未通过数；空观察不计入已记录或已通过。保存试用记录与最终交付使用不同动作和说明，未通过的记录可带入修改版。版本摘要展示初版/修改版、当前阶段及本次修改；待验收包与已交付包采用不同状态和下载文案。

#### 整洁度（本版起写入验收观感）
1. **少标签**：栏头一句职责即可，避免大段说明文案堆在栏内。  
2. **低密度**：空态一句话；进行中只突出当前阶段与下一步动作。  
3. **角色过滤**：PM 视图隐藏工厂内部阶段细节与度量；开发者可展开。  
4. **表单层级**：卡片内明确标题、状态、输入区与动作区，错误与保存状态就近呈现，不依靠长对话查找当前操作。
5. **参考**：`product-manager-workbench` 的留白与信息层级，不追求像素级复刻。

### 3.4 可理解失败态（报错对人话）

自动段失败时，两个角色看到的信息不同：

| 角色 | 看到什么 |
| --- | --- |
| **PM** | 一句人话「哪一步没做成」+ 一句「怎么办」（建议动作）；**不出现** eval / subprocess / sandbox / 熔断 等技术词 |
| **开发者** | 技术原因（原始 failure_reason）+ 失败阶段 + 可看日志/证据；保留重测/整段重跑入口 |

失败分类 → PM 话术 + 建议动作（MVP 覆盖以下六类，未覆盖的进「其它」）：

1. **内容没通过安全检查**（用了不安全写法）→「生成的内容没过安全检查」→ 建议「换个说法再试」或「整段重跑」
2. **生成的代码有问题**（语法/结构/依赖缺）→「生成的代码跑不起来」→ 建议「整段重跑」
3. **主路径接口缺失**→「成品少了个必需接口」→ 建议「整段重跑」
4. **模型调用失败**（Key 或网络）→「模型没连上，多半是 Key 或网络问题」→ 建议「检查 Key 后重试」
5. **流水线卡死超时**→「这一步做太久，已被中断」→ 建议「整段重跑」
6. **其它 / 未知**→「这次没做成功」→ 建议「整段重跑」，并提示可切开发者看原因

**原则**：PM 视图永远给「人话 + 下一步」；技术细节只在开发者视图展开，不把底层报错直接甩给 PM。

## 4. 什么算「造得好」（验收标准）

### 4.1 MVP 成功定义（本版唯一硬标准）
一次 Run 在人工验收通过后，满足：

1. 有书面 PRD（人已确认）且与主路径一致  
2. 产物可在本机按说明启动（一条或少量命令）  
3. 验收清单主路径全部为「是」（由人勾选）  
4. 决策台账完整（关键决策均有人答）  
5. 本轮新增 Run 在确认 PRD 前明确 3–10 条具体任务（标题、输入、预期结果），人工验收时逐项填写实际观察且全部通过；失败或未完成可保存为试用草稿
6. 可下载完整本地交付包，包内状态、版本和验收结果与该 Run 一致

历史 Run 保留原基础清单兼容，不追溯伪造真实任务记录。自动检查只证明相应技术检查通过；不替用户判断业务结果。任务验收不等于需求有市场、获得用户留存或形成付费意愿。

**不要求**：公网域名、生产级安全性、完整多租户、像素级设计完美。

### 4.2 质量判断
- PM：主路径是否符合想法、文案是否可懂、预览是否「像那么回事」
- 开发者：能否复现启动、代码是否在工作区可定位、失败日志是否可读
- 打分样例：2026-09-24 用 8 条真实想法打分——5 走通 / 2 半通 / 1 卡住（详见 `docs/PRD/版本/V1.1/验收证据/样例打分.md`）
- 判定「生成得好」：简单工具类（计算/点单/待办/起名/推荐/记账）应稳定走通；图像/视频类单独验证（当前不稳，待修）

上述 8 条是项目内部的混合场景样例，包含 6 条简单工具与 2 条图像/视频需求；5/8 是全样例走通比例，不能写成简单工具类通过率、8 名外部用户或生产成功率。后续修复已在状态文件中记录，但没有同口径完整复测结果前，不覆盖这次历史评分。

### 4.3 后续（非本版必达）
接近可上线：部署脚本、账号隔离、监控与回滚等——单独立项，不挤占 MVP。

### 4.4 真实用户与留存验证

**现状与范围。** 已有外部试用，留存尚未统计。本节定义后续验证方案；事件采集、分组统计和分析报表尚未作为本轮实现交付。以真实外部试用者为统计对象，排除项目负责人自测、内部调试、自动化测试与 mock 演示；辅助完成与自主完成分别报告。

**验证顺序。** 先记录外部试用者的真实任务与首次交付，再观察是否回来继续造应用，最后了解所生成应用是否在真实场景持续使用。应用制作可能是间歇需求，优先看按周复用，不把每日登录作为本阶段主要目标。

| 指标 | 定义与分母 | 当前状态 |
| --- | --- | --- |
| 外部有效试用人数 | 按匿名试用者去重，至少主动提交一个自己的真实任务；收到邀请或观看演示不计入 | 已有外部试用，具体人数待统计 |
| 7 日首次交付转化 | 首次主动提交后的 168 小时内完成第一次人工验收的人数 / 已满 168 小时观察窗的有效试用人数；自主与辅助完成分列 | 未统计 |
| 首次价值时间 TTFV | 首次主动提交到首次人工验收的实际经过时间，包含等待与人工操作；同时报告完成数 / 试用数，避免只呈现成功者耗时 | 未统计；现有自动执行耗时不等于此项 |
| W2 有效回访率 | 首次验收日期记为 D0，D7 至 D13 再次完成 PRD 确认或产物验收的外部用户数 / 已完整经过 D13 的首次验收用户数；按 Asia/Shanghai 自然日 | 未统计；仅打开页面不算有效回访 |
| 再次成功交付人数 | 首次交付后 14 日内，由用户主动发起另一轮 Run 并再次验收的人数；区分同项目继续尝试与新需求 | 未统计；自动定时创建不计入 |
| 生成应用持续使用 | 首次交付后约 7 日回访，确认应用是否再次用于真实任务，并记录用途与停止使用原因 | 待回访；工厂没有成品端使用埋点 |

所有比例同时报告分子、分母、观察期与完成方式；观察窗未满者单列。缺少事件或无法追溯时写「未统计」，分母为零时写「不适用」，均不记为 0% 留存。新用户尚未成熟与已流失用户不能混在同一分母中。

**最低记录方案。** 初期可先人工维护匿名试用台账：试用者编号、真实任务、首次提交时间、首次验收时间、对应项目/Run、是否依赖工程协助、再次有效使用时间、再次交付时间、应用使用反馈及卡点。已有 StageEvent、Confirmation 和 Run 可以帮助追溯执行节点，但不能自动识别外部用户、自主操作或成品端使用。

后续若加埋点，至少记录 `trial_started`、`prd_confirmed`、`delivery_accepted`，附匿名试用者、Project/Run、发生时间、操作者类别、触发来源、模型模式与完成方式；事件去重，明确手动与定时触发。以上是建议的数据约定，不是现有 API。生产留存应从用户真实操作计算，不能从定时 Run 数推断。

**留存假设与行动。** 历史项目和产物可找回，可能促使用户继续既有需求；可解释失败与重试可能降低放弃；确认后的可运行结果可能促成下一次新任务。通过回访记录检验这些原因。先收集一批完整观察窗建立基线，再决定转化与留存目标，不预设已达成数字或因果结论。

## 5. 交付阶段与优先级

### 5.1 第一刀（立刻做，对应工作台对标）
1. **项目 / 工作区绑定**：创建产品项目；可选附着本地目录；Run 按项目分组  
2. **产物一等公民**：右栏产物树 + 预览（PRD / 代码 / 运行说明）；结束「只靠聊天气泡交作业」  
3. **会话与产线分离 + 人审闸门**：中栏会话服务产线；决策 / 确认 / 验收三闸门强制人工  

### 5.2 第二刀（MVP 闭合）
- 本地可运行检查自动化（启动探测 + 主路径烟测或脚本）
- PM / 开发者视图切换（同一项目，信息密度不同）
- 失败可解释、可重试；取消 Run

### 5.3 第三刀（增强，可后置）
- 多模型对比工位、定时无人值守、多 Agent 分工看板  
- 接近可上线与桌面壳加强  
- 对外账号与商业化  

截至 2026-10-04 的实现核对：Run 级 mock/DeepSeek 选择、每日定时草稿、串行工位看板和 Electron 桌面壳已在代码与阶段记录中体现；「多模型」不代表已完成多家真实模型评测，「多 Agent 看板」不代表并行 Agent 协作，定时任务仍停在人审点。桌面壳不等于自包含发行安装包；公网与商业化继续后置。

后续优先级建议：先围绕外部用户的首次独立交付、卡点修复和回访记录迭代，再按证据决定是否扩展增强能力。本建议不自动开启新开发阶段。

### 5.4 本轮已授权增强（2026-10-05）

保留现有小应用代码生成与三栏工作台，补齐四项能力：需求补充纠错；继承已有成品的父子版本修改；具体任务试用、失败记录保存及人工验收；完整本地交付包下载。实现期间以项目状态和本轮证据更新完成情况。网页在线运行、邀请试用、用量预算、企业协作和生产部署继续后置，不替换成只有固定文本输入输出的工具平台。

同日的 UI 重构只调整前端视觉与信息层级，使用本节已有能力和接口：创建首页、场景模板、项目搜索、四步进度、审核页签、验证统计、交付状态及移动端抽屉。API、生成管线与上线范围不因此扩展，详细实现与当前检查结果见 [工作台 UI 重构](技术文档/工作台UI重构.md)。

本轮已通过前端测试、类型检查与生产构建，并在 1440×900 桌面、390×844 窄屏核对 Mock 创建至待验收、失败记录保存和改版表单回流等界面路径；刷新后记录保留。这些结果验证界面与数据流，不表示已执行成品正式验收通过或真实模型质量评测，完整范围见上述技术说明与项目状态。

## 6. 模型与成本

- 用户自备 Key；本地默认提供 mock 以便零成本走通产线
- 密钥不进仓库、不进前端、不在对话/日志/截图中回显
- 单次 Run 成本上限：待实测后写入状态台账；创建付费云资源前必须人确认

---

## 7. 数据与非功能

- 国内部署取向；业务数据默认不出境
- 项目、Run、决策、产物元数据持久化；进程重启可恢复
- 数据持久化用于找回项目和状态；「数据留存」不等于「用户留存」。用户行为验证见第 4.4 节。
- 用户数据按登录账号隔离（已有手机号验证码登录可沿用；短信正式接入后置）
- 长任务需看门狗：无进度超时失败；等待人工确认不算卡死

---

## 8. 安全与权限

- 写工作区、执行安装/启动命令：默认可配置为需确认（开发者可「本 Run 始终允许」）
- 高风险 / 付费 / 对外发送：必须人确认，不交给模型自主
- PM 默认不能执行「危险调试」类动作；开发者角色可见

---

## 9. 界面与交互原则

- 当前任务与下一步动作优先，生成过程和历史对话可展开查看；产物与预览保留独立入口
- PM 文案用产品语言；技术细节折叠到开发者视图
- 首页以居中的想法输入和三张场景模板引导创建；选中项目后以阶段工作卡推进，项目资料按需呈现
- 视觉：采用浅灰画布、白色表面与蓝色主操作；正文深色、说明灰色，使用统一卡片、表单、按钮和 Lucide 图标。卡片圆角 12px、控件圆角 8–10px，保留清楚的边界、留白和状态层级，不使用渐变或 emoji 承担主界面信息
- 当前 UI 契约替代此前近黑工作台的视觉约定；既有业务能力、人工确认与验收边界保持有效，桌面和手机交互需分别验证

## 10. 与 V1.0 的关键差异

| 项 | V1.0 | V1.1 |
