# 本地验证与交付增强

日期：2026-10-05。范围来自本轮用户确认：在原项目上增强，保留小应用代码生成，本地生成、运行、交付优先；服务产品经理的工作提效和独立创作者的产品想法验证。

## 产品行为

1. 等待决策或 PRD 确认时，用户可提交补充纠错，保留反馈历史并重新生成待审核 PRD。
2. 确认前可编辑 3–10 条具体任务，每条有标题、输入、预期结果。新建界面启用任务验收，历史 API 默认基础模式兼容。
3. 待验收时可保存尚未通过的试用记录；最终交付要求完整任务全部通过、实际观察非空，并通过原基础清单。
4. 已生成应用可创建同项目子版本。生成上下文包含父 PRD、代码快照、验收场景和实际结果，保留父成品与历史。
5. 下载包包含应用、运行说明、PRD、决策及验收记录。待验收包和已交付包分别标识。

## 接口约定

统一前缀 `/api/v1`，沿用登录认证、Run 所有权检查和 `error.code/message` 错误结构。

| 接口 | 主要请求 | 结果 |
| --- | --- | --- |
| `POST /runs/{id}/requirements` | `feedback` | 保存反馈、重建 PRD，返回 Run |
| `PUT /runs/{id}/acceptance-scenarios` | `scenarios: [{id,title,input,expected_output}]` | PRD 确认前保存，返回 Run |
| `PUT /runs/{id}/acceptance-results` | `scenario_results: [{scenario_id,passed,observation}]` | 保存试用草稿，允许未通过，返回 Run |
| `POST /runs/{id}/accept` | 原 `checklist` 加 `scenario_results` | 校验完整性后保存人工验收 |
| `POST /runs/{id}/revise` | `change_request`, 可选 `request_id` | 新建关联父版本的 Run；重复请求可幂等复用 |
| `GET /runs/{id}/bundle` | 无 | 带下载文件名的 ZIP |

Run 增加父版本、修改要求、需求反馈历史、验收模式、场景、试用结果、基础清单和验收时间。数据库采用追加列的迁移，保留原 Run。变更上下文用于后续模型输入，不能只保存在界面。

## 检查和交付边界

主路径烟测必须返回 2xx，4xx/5xx 均失败。HTTP 成功不代表业务质量通过，实际任务由用户验证。

交付包只收集本 Run 的受控生成产物和记录，保留 `deploy/` 目录与启动脚本执行权限，排除真实环境密钥、内部数据库、日志、缓存和符号链接。下载需当前账号拥有该 Run，失败或取消任务不当作可交付成品。具体白名单与限额见 `backend/app/services/delivery.py`。

PRD 使用 `prd_revision` 防止看过旧稿的迟到请求批准新稿；场景更新也会递增 revision。新场景模式确认时需提交当前 revision，旧基础模式兼容原请求。确认后的 `output_type` 统一用于代码生成与产物检查，避免否定句中的旧视频词影响新版本。

本轮自动化验证使用 mock，不以其结果替代真实模型质量或外部用户验收。执行结果见 [验证记录](../验收证据/本地验证与交付增强/验证记录.md)。
