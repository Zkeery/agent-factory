# 人工验收不通过与修复

日期：2026-10-05。版本仍为 V1.2。当前契约见 [V1.2 PRD](../PRD.md)，进度见 [项目状态](../../../../项目状态.md)。

## 问题与范围

用户反馈五子棋人机模式 AI 不落子，并指出验收没有「不通过」路径。本轮分开处理已生成五子棋的本地回合调度，以及工厂的失败记录、修复草稿和新版本入口。

最新 Run `8403cd0e-c0a9-42e5-b74c-c844cb7448a0` 的 `app.py` 中，`handleClick` 玩家落黑子后漏调用 `scheduleAI`。主 Agent 在本地预览 8003 复现：玩家落子后一直轮到白方，AI 回合没有执行。该人机对手是本地 JavaScript 搜索策略，不调用 DeepSeek；根因是回合调度缺失，并非模型调用失败。

最新已生成版本已补齐调度，隔离 JavaScript 11 场景回归通过；真实浏览器连续 5 次黑子落子均有白子自动回应。历史父版本（2be…）保留，本轮不把历史版本改写为已修复。工厂修复子版的桌面/手机交互已完成 Mock 联调；Run 仍待人工验收，不宣称用户已人工业务验收通过。

## 人工验收与修复合同

| 环节 | 当前行为 |
| --- | --- |
| 场景判断 | 明确选择未验证/通过/不通过；未验证不等于失败。 |
| 保存场景记录 | 继续使用原 results API，保存人工结果，不自动交付。 |
| 修复未通过场景 | 只有明确不通过且填写实际结果的场景可进入；草稿带 input、expected、actual。 |
| 基础验收不通过 | 输入原因，通过 `POST /api/v1/runs/{id}/reject` 保存 `{note}`；问题持久保存，Run 保持待人工验收，不标记交付。 |
| 修复草稿 | 根据已保存问题形成不超过 4000 字符的可编辑草稿；生成草稿本身不调用模型。 |
| 确认创建新版本 | 用户确认后才调用原有生成 API，使用既有模型配置；原版本与问题记录保留。 |
| 正式交付 | 仍需人工明确确认通过；保存失败或修复草稿都不能代替通过确认。 |

场景失败信息要保留原输入、预期和实际观察，以便子版本复验；不能把未验证场景混入失败集合。基础验收的问题原因经过持久化保存，再带入修复草稿。两条路径都保持「记录问题 → 检查草稿 → 确认创建新版本」的顺序，不在保存不通过时自动重生成或调用用户模型。

本轮工厂联调只使用 Mock，不调用用户 DeepSeek。后续用户确认创建真实修改版时才执行原模型链路；这与五子棋运行时的本地搜索策略是不同环节。

## 2026-10-10 验收只问主流程

上面 2026-10-05 的合同记录的是当时的多场景验收。现行规则改为每次验收只问一个问题：主流程是否走通。

| 环节 | 现行行为 |
| --- | --- |
| 确认前 | 新运行只编辑主流程：怎么操作、怎样算走通。需求文档仍至少保留三条验收标准。历史多条场景在保存时一并留下，验收时不再逐条提问。 |
| 试用 | 打开成品，选择「走通了」或「没走通」。 |
| 交付 | 主流程走通后可以验收交付。场景模式把这条结论写入验收记录；基础模式记录主流程确认。 |
| 其他问题 | 主流程没走通，或走通了但仍有其他问题，用户自由填写反馈。空反馈不能进入修改。走通后的其他问题不把主流程记为未通过。 |
| 修改版 | 反馈保存在当前版本，版本保持待人工验收。草稿带入修改要求，用户确认后才创建修改版。 |
| 历史记录 | 已经保存的多条观察仍可查看和导出。进行中的旧版本不要求把每条场景再答一遍，交付只看主流程。 |
