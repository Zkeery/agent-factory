# 第 5 阶段技术开发文档｜运行监控与看门狗

> 配套文档：《Agent造物坊 PRD V1.0》、《技术适配声明》、第 1-4 阶段技术开发文档。
> 本文档只覆盖第 5 子阶段（运行监控/看门狗）。不提前实现后续能力。

## 一、阶段目标

让工厂流水线**不会一直挂着烧钱**：跑太久没输出、卡在工具调用、连续失败时，自动熔断/标记失败，而不是无限等待；超时未证明"还活着"一律按异常处理。失败后可人工介入（重试）。

## 二、技术适配摘要

- 沿用现有技术栈，不新增框架。
- 新增内置看门狗线程（区别于已有的外部脚本 `backend/scripts/monitor.py`，内置到服务进程，随服务启停）。
- 复用现有 `_mark_failed`（失败标记）+ `stage_events`（心跳记录）。

## 三、技术栈与模型

- 不变。看门狗用确定性代码，不调模型。

## 四、环境与配置

新增配置（`.env.example` 同步）：
- `RUN_STUCK_TIMEOUT=300`（run 卡死阈值，秒；超过此时间无进度判定卡死）
- `WATCHDOG_INTERVAL=30`（看门狗扫描间隔，秒）

## 五、项目结构

```text
backend/app/
├── core/config.py       # 加 run_stuck_timeout / watchdog_interval
├── services/watchdog.py # 新增：看门狗线程 + 卡死扫描
└── main.py              # 启动时拉起看门狗
```

## 六、数据、资产与状态

- 心跳：run 每次推进（`stage_events` 新增）时，`factory_runs.updated_at` 已由 onupdate 自动刷新。
- 卡死判定：`status='running'` 且 `current_stage` 不在等待人工态（awaiting_answers / awaiting_prd_confirm），且 `now - updated_at > RUN_STUCK_TIMEOUT` → 判定卡死。
- 卡死处理：标记 `failed` 终态 + 落 error 事件（code=`run_stuck`，message 说明卡死超时）。

## 七、API / 工具设计

- 无新增对外接口；失败态通过现有 `GET /runs/{id}` 与 SSE error 事件透出。
- SSE 在 failed 态发 `event: error`（已有），前端展示失败原因。

## 八、Prompt 设计

- 无新 Prompt。

## 九、验收界面或纵向切片

- 前端第 3 阶段（任务列表 + 重试）将展示失败原因与重试入口；本阶段后端先行，不新增界面。

## 十、测试要求

- 第一层 mock 测试：
  1. 卡死 run（running + 非等待态 + 超时）被看门狗标记 failed + error 事件。
  2. 等待人工态（awaiting_answers/awaiting_prd_confirm）不被误判。
  3. 未超时的 running 不被误判。
  4. 终态（gate_passed/gate_failed/failed）不参与扫描。
  5. 回归：第 1-4 阶段测试保持通过。
- 第二层真实冒烟：本阶段无新模型契约，不重复真实调用。

## 十一、验收清单（产品经理照着做）

- [ ] 后端正常跑通完整流程（不卡死）
- [ ] （可选）人为制造一个卡死 run，观察看门狗在阈值后标记失败并透出原因

## 十二、风险与待确认项

- 阈值默认 300 秒（真实模型链路约 10 秒，5 分钟是宽裕值）；可配置调整。
- 看门狗只标记"无进度"的卡死，不打断正在执行的模型调用（模型调用本身有 120s 超时）。
- 必须由产品经理决定的问题：无。

## 十三、交接给下一阶段

- 就绪：失败/卡死有统一终态与原因，供前端第 3 阶段展示「失败原因 + 重试」。
- 下一阶段：前端第 3 阶段（任务列表 + 刷新恢复 + 失败重试）。
