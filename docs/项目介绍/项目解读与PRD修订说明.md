# Agent造物坊 项目解读与 PRD 修订说明

核对日期：2026-10-04。依据项目 PRD、状态记录、关键实现及历史验收材料，并参考指定聊天“运行 AI造梦机 项目”中的 PRD 与项目经历。

**结论：需要修改 PRD。** 现有版本较完整地定义了“要做什么、怎样实现、如何验收”，但个人项目的动机、外部试用与持续使用验证不足。本次已补齐这些内容，并另写三段式项目经历。项目目前可表述为“本地核心闭环已落地，已有外部试用”；用户规模与留存仍待统计。

## 项目概述

### 为什么做

Agent造物坊帮助有小工具想法、缺少编码与调试经验的非技术产品经理，把需求推进为可在本地使用的小应用。用户的困难贯穿几个环节：想法不够具体，不知道需要作哪些决定；得到代码后不会判断是否能运行；遇到错误时不知道该改需求还是重试；完成后又难以找回决策、说明与产物。

因此，这个个人项目值得讲的价值是：**把“提出想法”和“拿到可验收结果”之间的工作组织起来。** 关键问题由人决定，重复生成和基础检查交给系统，最终由用户确认主路径是否解决了自己的需求。这个动机能够被现有产品设计支持，但尚无系统访谈或对照实验足以证明普遍需求强度、效率提升或付费意愿。[S1][S3]

用户价值验证应优先围绕非技术 PM。开发者视图帮助协作、复现与排障，不能用“工程师帮忙跑通”替代“目标用户能独立完成”。现有双视图继续保留，这是验证重点的明确，不是删除开发者功能。

### 最小闭环是什么

**真实任务 → 关键决策 → PRD 确认 → 代码与运行说明 → 本地检查 → 人工验收 → 项目归档。**

以“做一个能添加、完成和删除事项的待办工具”为例：用户明确任务与范围，确认 PRD，系统生成应用和运行说明并检查，用户在预览中实际操作主路径后验收。该示例说明验收方法，不是新增外部用户案例。

| 环节 | 系统完成什么 | 用户作什么判断 | 何时不能算成功 |
| --- | --- | --- | --- |
| 需求澄清 | 生成决策卡并保存答案 | 关键范围与方向是否正确 | 仍有关键问题未回答 |
| PRD 确认 | 基于想法和已回答决策起草 PRD | 要做的事和完成标准是否一致 | 只生成文档但没有确认 |
| 实现生成 | 生成应用代码、依赖和 README | 必要时查看实现方向 | 代码文件存在但不可用 |
| 本地检查 | 语法、产物护栏、导入、启动和主路径烟测 | 查看自动检查结果 | 页面打开但核心任务不成立 |
| 人工验收 | 提供验收清单并保存确认 | 本地能跑、符合 PRD、无明显阻断 | 自动闸门通过但用户未验收 |
| 归档与继续 | 保留 Project、Run、产物与运行说明 | 继续旧项目或发起下一次尝试 | 把自动生成新 Run 当成用户回访 |

这里的完成单位是“一名用户的一次可验收任务”。项目、Run 和模型调用分别是组织单位、尝试单位和执行记录，三者不能互相替代。[S3][S4][S5]

### 项目实际如何工作

前端是 Next.js 三栏工作台，分别组织项目、对话与人工确认、产物与预览；PM 视图强调结果和下一步，开发者视图展开技术信息。后端以 FastAPI、SQLite 和确定性状态机推进任务，状态、决策、确认与产物元数据持久保存，前端通过 SSE 展示进度。[S2][S3][S5]

模型主要参与澄清、PRD 和代码生成。真实调用采用 DeepSeek 的 OpenAI 兼容接口，另有 mock 用于本地演示与测试；已回答的决策进入 PRD Prompt，已确认 PRD 进入代码 Prompt。输出经过结构解析与有限重试，生成代码经过语法和运行检查。这个实现适合表述为“LLM 驱动的分阶段应用生成与状态机编排”。[S3][S6]

它目前没有足够证据支持“自主规划的并行多 Agent 平台”“完整 RAG 知识库”或“通用多模态生成平台”的表述。图像和视频相关能力主要表现为生成应用的产物要求、演示回落及检查护栏；不能从代码包含视频或图片处理，就推导出真实多模态模型效果已经成熟。[S6][S8]

### 真实用户与留存现状

项目负责人在本次沟通中确认：**已有外部试用，尚未统计留存。** 这比只有内部演示多了一项真实用户信号，但还不足以判断用户规模、激活率、独立完成率、复用频次与付费情况。项目材料中的 8 条想法是内部场景测试，不能改写成 8 名试用者。

需要分别回答两类持续价值问题：

- **工厂复用：** 用户是否回来继续一个项目，或提出新的小应用需求，并发生 PRD 确认或产物验收等实际行为。
- **成品使用：** 用户生成的小应用是否继续用于真实任务。用户离开工厂后仍在使用应用，也可能获得价值；工厂中的登录和 Run 数看不到这部分。

因此，留存设计应围绕按周复用和成品回访。当前没有这些数据，不能把“项目状态能保存”或“自动任务每天运行”写成“用户持续使用”。

## 职责描述

### 应当突出哪些产品工作

个人项目的职责可以概括为：**负责从 0 到 1 的产品规划与 AI 辅助研发落地，将需求定义、自动生成、人工验收和真实用户验证连接起来。** 写专业术语时，要同时写清对应的设计或决策。

| 职责方向 | 项目中有依据的具体工作 | 对用户的价值 |
| --- | --- | --- |
| 产品定位与方案设计 | 定义本地小应用的交付标准，统筹 PRD、三栏工作台、双视图与迭代优先级 | 明确首次任务的范围、操作路径与完成标准 |
| AI 编排与生成策略 | 状态机与 HITL、阶段化 Prompt、结构校验、运行检查与失败重试 | 生成可检查，关键环节可由用户介入 |
| 产品验证与用户留存 | 质量评估和问题归因；首次交付、TTFV、有效回访与再次交付口径 | 后续迭代围绕真实任务与持续复用展开 |

这三类能力构成产品的核心方法。定时草稿、工位看板和桌面壳是已有增强能力，但功能数量本身不能证明用户愿意再次使用。下一轮迭代建议由外部试用卡点决定，而不是默认继续增加工位或模型选项。

### 参考 AI造梦机时应借鉴什么

指定聊天中的主要成品是项目说明与项目经历；其 PRD 也补写了用户问题、场景、需求和验收依据。本次借鉴这套表达方法，并采用“项目概述—职责描述—项目成果”的结构。两个项目的事实、功能与数据分开核对。[S10]

| 参考方法 | Agent造物坊的对应写法 |
| --- | --- |
| 先讲用户任务和问题 | 非技术 PM 如何从模糊想法拿到可验收的小应用 |
| 用产物和确认关系解释架构 | 决策传入 PRD，确认后生成代码，检查后人工验收 |
| 职责使用专业名称并解释动作 | 状态机编排、HITL、Prompt Engineering、结构化输出与 Bad Case 分析 |
| 成果引用可核对的数字 | 有依据的产品交付、外部试用现状与用户验证方案 |
| 把需求、实现和验证边界写清 | 已有外部试用；留存和自主完成率未统计 |

AI造梦机的 RAG、Embedding、多模态模型、成片数量和评测数据不能迁移为 Agent造物坊的成果。个人项目也不必套用“商业化已完成”的口吻；从零到一落地、真实试用与可验证的后续假设，已经能形成完整叙事。

### PRD 已修改哪些内容

保留 V1.1 的开发契约和原有章节编号，新增个人项目论证与用户验证内容；三段式表述独立保存为项目经历，避免把开发规格压缩成简历条目。

| 位置 | 原有问题 | 本次修订 |
| --- | --- | --- |
| 第 1 节 | 从角色和功能开始，动机不足 | 补为什么做、目标用户任务、已有外部试用及证据边界 |
| 第 1.3 节 | 功能链路清楚，价值终点不够突出 | 明确人工验收与归档才完成一次闭环，辅助完成单列 |
| 第 4.2 节 | 8 条样例容易被误用为用户数据或通用成功率 | 明确混合场景分母和历史评分性质，修复不自动覆盖旧评分 |
| 第 4.4 节 | 没有首次交付和留存口径 | 增加试用人数、7 日转化、TTFV、W2 回访、再次交付与成品使用 |
| 第 5.3 节 | 增强规划与已落地内容混在一起 | 补实际边界：Run 级模型选择、串行看板、定时草稿、桌面壳 |
| 第 7、9、11 节 | 数据留存易误读；视觉和开放问题滞后 | 区分数据保存与用户留存，同步已记录视觉，更新待验证问题 |
| 文档导航与状态 | 常用 PRD 链接仍指向 V1.0 | 指向当前 V1.1，登记本轮用户事实与文档修订 |

本次没有新增埋点、统计报表或业务功能，也没有重做历史验收。留存方案是可执行的下一步定义，不能计入已达成用户增长成果。

### 当前功能应怎样准确命名

| 现有名称 | 建议对外表述 | 依据与限制 |
| --- | --- | --- |
| 多模型工位 | Run 级模型配置与来源记录 | 当前入口主要为 mock / DeepSeek，未见多家真实模型评测结果 |
| 多 Agent 分工看板 | 串行工位状态与产物可视化 | 阶段文档明确未改为并行多 Agent 架构 |
| 定时无人值守 | 定时启动草稿，等待人工决定 | 遇到决策、PRD 确认、验收仍停下 |

| 图像和视频支持 | 图像与视频应用的产物护栏及独立样例验证 | 演示文件可打开，不等于模型生成质量达到使用要求 |

这些边界来自关键实现与阶段说明，不是对产品前景的判断。[S6][S7][S8][S9]

## 项目成果

### 已经有依据的成果

1. **从 0 到 1 完成产品设计与落地。** 打通需求确认、应用生成、本地运行与人工验收，形成包含项目管理、产物预览和历史记录的最小交付闭环。

2. **推动产品进入外部试用。** 沉淀需求与验收规范，建立覆盖首次交付、有效回访及再次交付的验证口径，支撑用户反馈与产品迭代；留存数据待统计。

### 现有数据能够说明什么

| 数据或材料 | 能支持的结论 | 不能支持的结论 |
| --- | --- | --- |
| 8 条样例与人工评分 | 某轮内部场景测试结果与失败类型 | 8 名外部用户、生产成功率 |
| delivered Run 占比 | 当前数据集合中人工交付状态的比例 | 外部用户激活率或留存率 |
| 平均 duration_seconds | 已记录执行片段的平均耗时 | 用户从首次输入到第一次可用结果的完整耗时 |
| token 与 cost_estimate | 按配置单价计算的模型成本估算 | 实际扣费、收入、利润或付费转化 |
| 项目与 Run 持久化 | 可以保留执行上下文和历史产物 | 已经发生用户复用 |
| 用户确认已有外部试用 | 存在外部使用这一事实 | 自主完成数、试用规模与持续使用效果 |

目前 metrics.py 汇总的是 Run 级工程指标，并未把真实外部用户、测试与演示统一分组。用该接口直接写产品增长结论，会混淆统计对象。[S7]

### 真实用户与留存如何补证

初期建议先用匿名台账补齐已发生的试用，逐人记录真实任务、首次提交、首次人工验收、是否需要工程协助、后续实际行为及停止使用原因。已有阶段事件与确认记录可辅助追溯，但姓名、联系方式和密钥不需要写入项目经历。

| 要回答的问题 | 推荐指标或方法 | 当前结论 |
| --- | --- | --- |
| 用户是否获得第一次价值 | 7 日首次交付转化；TTFV，包含人等系统和系统等人的时间 | 未统计 |
| 用户是否回来继续制作 | 首次验收 D0 后，D7–D13 完成 PRD 确认或人工验收的 W2 有效回访率 | 未统计 |
| 用户是否再次拿到可用结果 | 首次交付后 14 日内再次成功交付人数，区分旧项目和新需求 | 未统计 |
| 小应用是否真的有用 | 约 7 日回访是否再次用于真实任务、具体用途与放弃原因 | 待回访 |

统计约定已写入 PRD 第 4.4 节：人数去重、真实外部试用、完整观察窗、自主与辅助完成分列；排除测试、mock、创始人自测及定时自动创建。比例必须同时给出分子和分母。数据不足写“未统计”，不能填成 0%。

是否回访与是否有新需求应一起解释。若用户只需要做一次工具，工厂回访低但成品持续使用，后续可以研究交付后支持；若用户有连续需求却无法再次成功，则应优先修复生成与使用卡点。这些是待验证判断，不预设结论。

### 下一阶段最值得做的三件事

1. **补齐现有外部试用台账。** 确认真实任务、谁实际操作、首次结果和工程协助程度。先得到可核对的事实，建立基线。
2. **完成一轮有观察窗的回访。** 区分继续原项目、发起新需求、只使用生成应用和彻底放弃，记录具体原因。
3. **按最常见阻断迭代。** 优先解决无法独立完成、首次结果不合意、失败后无法继续等问题；修复后复测相同样例，再决定是否扩大模型、桌面与定时能力。

不建议在尚未拿到上述证据时，把重点转向复杂的多 Agent 并行或商业化模块。当前最关键的产品问题是外部用户能否独立获得价值、为何愿意再次使用。
